# Backend Plan

`specs/backend/spec.md`를 어떻게 구현할지 (HOW).
기술 선택은 사용자가 결정한 뒤 "무엇을 골랐고, 왜, 무엇을 포기했는지"로 기록한다.

---

## 기술 결정

| # | 결정할 내용 | 선택 | 이유 | 포기한 것 |
| --- | --- | --- | --- | --- |
| B1 | DB 접근 방식 | Spring Data JPA (Hibernate) | 가장 널리 쓰이는 표준 방식. 단순 생성 · 수정 · 조회를 적은 코드로 처리하고 변경 감지를 쓸 수 있음 | 목록 · 잠금 쿼리는 JPQL / 네이티브 SQL로 따로 작성해야 함. 지연 로딩 · N+1 · 영속성 컨텍스트를 의식해서 다뤄야 함. 의존성 추가 |
| B2 | 스키마 관리 | `schema.sql` + `spring.jpa.hibernate.ddl-auto: validate` (잠정, 필요하면 변경) | 제출 시점의 완성된 스키마 하나만 필요하고 운영 중 변경 이력이 없음 → 마이그레이션 도구(Flyway)는 과함. 스키마가 파일로 드러나고, 인덱스 · 제약을 SQL로 직접 정할 수 있음(부분 인덱스 등 PostgreSQL 전용 기능 포함). `validate`가 엔티티와 테이블 불일치를 기동 시점에 잡음. `ddl-auto: create`는 재기동마다 데이터를 지워 요구사항(P-65)과 충돌해 제외 | 스키마 변경 이력이 남지 않음. 엔티티와 SQL 두 곳을 함께 고쳐야 함. 개발 중 스키마를 바꾸면 기존 볼륨에 반영되지 않아 `docker compose down -v` 필요 |
| B3 | 시드 적재 주체 · 시점 | 백엔드 기동 중, **웹 서버가 포트를 열기 전**에 Java 코드가 `APP_SEED_PATH`의 JSON을 읽어 적재 (`SmartInitializingSingleton` + `TransactionTemplate`; `ApplicationRunner` 미사용) | 제공된 compose 마운트(`/seed`, `APP_SEED_PATH`)를 수정 없이 사용. 원본 JSON을 직접 읽어 변환본이 필요 없음. 삭제 표시 · 시퀀스 보정 같은 후처리를 같은 코드에서 처리하고 테스트로 검증 가능. 적재가 끝나야 포트가 열리므로 적재 중 `/health` · API 요청이 들어오는 상황이 **구조적으로 생기지 않음** → `HealthController`를 건드릴 필요 없음 (B10-a 유지). `ApplicationRunner`는 웹 서버가 이미 요청을 받는 뒤에 실행되어 이 보장이 없음 | "이미 적재됨" 판단(B4)을 직접 구현해야 함. 적재 시간만큼 기동이 늦어짐 (2천여 건이라 미미). `ApplicationRunner`보다 덜 흔한 지점이라 README에 이유를 한 줄 적어야 함. 이 시점엔 `@Transactional` 대신 `TransactionTemplate`을 써야 함 |
| B4 | 시드 멱등성 판단 | `posts`가 비어 있을 때만 적재 + 전체 적재를 하나의 트랜잭션으로 | 행을 실제로 지우지 않으므로 한 번 적재되면 `posts`가 다시 비지 않음 → 추가 테이블 없이 판단 가능. 트랜잭션으로 묶어 부분 적재가 남지 않고, 실패하면 다음 기동에 처음부터 재시도. B3에 따라 적재 중에는 포트가 닫혀 있으므로 "적재 도중 사용자가 글을 써서 판단이 어긋나는" 경우가 생기지 않음 | "게시글 있음 = 적재됨"이라는 간접 추론 (DB를 직접 조작한 경우는 판단 못 함) |
| B5 | ID 생성 · 시퀀스 보정 | `GENERATED BY DEFAULT AS IDENTITY` + JPA `GenerationType.IDENTITY`. 시드는 id를 지정해 SQL로 INSERT하고, 같은 트랜잭션에서 `setval`로 게시글 · 댓글 시퀀스를 각 테이블 최대 id로 맞춤 | PostgreSQL · JPA 기본 조합이라 단순. 새 id가 시드 바로 다음(게시글 43, 댓글 2077)부터 이어짐. id를 지정해 넣으면 시퀀스가 따라오지 않는 문제를 명시적으로 해결 | `setval`을 빠뜨리면 첫 작성에서 PK 충돌 (게시글 · 댓글 둘 다 필요). Hibernate가 IDENTITY에서 INSERT 배치를 못 함 (이 과제의 쓰기량에선 영향 없음) |
| B6-a | 소프트 삭제 표시 | `deleted_at TIMESTAMPTZ NULL` (삭제 전 NULL) | 삭제 여부와 삭제 시각이 함께 남음. 소프트 삭제의 일반적인 형태 | 조건이 `IS NULL` / `IS NOT NULL`이라 boolean보다 덜 직관적 |
| B6-b | 삭제 행 필터링 | 쿼리마다 `deleted_at IS NULL`을 명시 (`@SQLRestriction` 미사용) | 쿼리에 보이는 그대로 동작. 삭제된 게시글 · 댓글을 찾아 `POST_DELETED` · `COMMENT_DELETED`로 구분해야 하므로(P-53, C5) 삭제 행을 조회할 수 있어야 함 | 조건을 한 곳이라도 빠뜨리면 삭제된 데이터가 노출됨 → 조회 경로별 테스트로 막아야 함 |
| B6-c | 삭제된 게시글의 댓글 (P-52) | 게시글과 댓글의 삭제 상태를 독립적으로 관리. 게시글을 삭제해도 댓글의 `deleted_at`은 바꾸지 않고, 댓글 접근 시 부모 게시글과 댓글의 활성 상태를 함께 확인 | 제공된 시드가 이미 이 모델로 표현되어 있음 (삭제된 게시글 9 · 30 · 31의 댓글 69개가 `deletedCommentIds`에 없음) → 시드와 앱의 규칙이 하나로 맞음. 댓글 요청은 어차피 게시글부터 확인하므로(C2-c, B-33) 추가 부담이 작음. 글 삭제가 댓글 수와 무관하게 한 행 수정으로 끝나고, "직접 삭제된 댓글"과 "글 때문에 숨겨진 댓글"이 구분됨 | 댓글의 `deleted_at`만으로는 삭제 여부를 판단할 수 없음 → 댓글을 다루는 모든 경로에서 부모 게시글 상태를 함께 확인해야 함 |
| B7 | `commentCount` 계산 | 조회할 때마다 댓글 테이블에서 계산 (`deleted_at IS NULL`인 댓글만). 별도 컬럼에 저장하지 않음 | 원본 데이터(댓글)에서 직접 세므로 값이 어긋날 수 없음. 댓글 작성 · 삭제 로직에 증감 처리가 없어 단순. 시드 적재 시 초기값 계산 불필요 | 조회마다 집계 비용이 듦 (현재 규모에선 무시 가능, 댓글이 크게 늘면 목록이 느려질 수 있음). 목록에서 게시글마다 따로 세면 N+1이 되므로 한 번에 묶어 세야 함 |
| B8-a | 좋아요 저장 | 누가 눌렀는지: `post_likes(post_id, user_id)` + 유니크 제약. 좋아요 수: 게시글과 분리된 `post_like_counts(post_id, like_count, version)`에 저장하고 증감 (시드 값으로 시작, 새 글은 0) | 시드 숫자를 그대로 시작값으로 사용. 읽을 때 집계가 필요 없음. 유니크 제약이 같은 사용자의 중복 좋아요를 DB 수준에서 막음. 좋아요 수와 버전을 게시글에서 분리해 **글 수정과 좋아요가 서로 다른 행을 건드림** → B8-b 낙관적 락이 글 수정과 충돌하지 않음 | 테이블이 하나 늘어남. 게시글 조회 시 좋아요 수를 함께 가져와야 함 (목록은 N+1 없이 묶어서). 게시글 생성 시 `post_like_counts` 행도 함께 생성해야 함. 기록과 숫자가 따로 저장되므로 같은 트랜잭션에서 함께 바꿔야 함. 시드 좋아요는 누가 눌렀는지 모르므로 기존 사용자도 처음에는 모두 "안 누름"(P-64) |
| B8-b | 좋아요 동시성 (D7 · B-41 · B-42) | `post_like_counts`에 `@Version` 낙관적 락 + 충돌 시 재시도. 좋아요 수는 엔티티에서 ±1 (Atomic Update 미사용) | 대안인 게시글 행 잠금(`SELECT ... FOR UPDATE`)으로도 D7을 만족하며 이 규모에서는 그쪽이 더 단순하다는 것을 전제로 한 선택. 좋아요는 읽기가 압도적이고 같은 사용자 · 같은 글의 쓰기 충돌은 드물기 때문에, **평소에는 잠금을 잡지 않고 처리하고 드문 충돌만 재시도**하는 방식을 택함. 하나의 장치로 같은 사용자 연타(D7)와 여러 사용자 동시 요청(숫자 누락)을 모두 처리: 같은 시점에 읽은 요청은 커밋 시 버전 충돌로 걸려 다시 읽고 재계산하므로, 연타는 "좋아요 → 취소" 순서가 지켜지고 숫자도 누락되지 않음. 버전을 게시글이 아닌 `post_like_counts`에 두어 좋아요가 글 수정을 실패시키지 않음 (B8-a) | 재시도 로직 · 409 응답 · 제약 이름 구분 · 트랜잭션 분리(Facade) · 분리 테이블까지 구현 범위가 행 잠금 한 줄보다 큼. 낙관적 락은 **충돌이 드물다는 전제**에서만 유리하며, 같은 글에 충돌이 잦아지면 실패한 시도마다 롤백 · 재조회가 생겨 행 잠금보다 느려질 수 있음 → 최초 포함 최대 3회로 상한을 둠 (B8-c). 버전 충돌과 `post_likes` 유니크 위반 두 예외를 모두 재시도 대상으로 다뤄야 함 |
| B9-a | 페이지네이션 방식 (+ Integration C1) | 커서(keyset). 정렬 `(created_at DESC, id DESC)`, 다음 묶음은 마지막으로 본 `(createdAt, id)`보다 뒤의 항목 | 페이지 사이에 최신 글이 추가되어도 offset 이동으로 인한 중복 · 누락이 발생하지 않음. 삭제로 남은 항목의 위치가 당겨져도 offset 방식과 같은 위치 이동 문제를 피함 (아직 보지 않은 항목이 다음 요청 전에 삭제되면 나오지 않는 것은 누락이 아니라 활성 데이터에서 빠진 것). 같은 시각 항목은 `id`로 순서가 정해져, 초 단위 정밀도(C4)에서도 경계에서 중복 · 누락이 없음. 댓글처럼 크기가 바뀌어도(2개 → 20개) 자연스럽게 이어짐. 몇 번째 묶음이든 조회 비용이 같음 | 특정 페이지로 바로 이동 불가 (무한 스크롤이라 불필요). JPA `Pageable` 기본 기능이 아니라 `(created_at, id)` 비교 조건을 직접 작성. 응답에 다음 커서 필드 추가 |
| B9-b | 커서 형태 | `createdAt`과 `id`를 별도 쿼리 파라미터로 전달 | 정렬 기준이 단순하고 API 소비자가 제한적이므로 디버깅 가능성과 구현 명확성을 우선. URL만 봐도 이어서 가져오는 기준이 보임 | 불투명 커서를 쓰면 클라이언트와 내부 정렬 기준의 결합을 줄일 수 있으나 포기함 → 정렬 기준이 바뀌면 API도 바뀜. 두 값이 항상 짝으로 와야 하므로 쌍 검증이 필요 |
| B10 | 패키지 구조 | 기능별: `post/` · `comment/` · `like/` · `seed/` · `common/` (각 기능 안에 Controller · Service · Repository · 엔티티 · dto) | 기능 하나의 코드가 한 폴더에 모여 기능 단위로 읽고 고치기 쉬움. 헥사고날 같은 추가 추상화 없이 Controller → Service → Repository 계층만 유지 | 기능 간 의존 규칙을 정해야 함 (B10-b). 계층 규칙이 폴더로 드러나지 않음 |
| B10-a | 기존 파일 위치 | `CommunityApplication` · `CorsConfig` · `HealthController`는 루트 패키지에 그대로 두고, 새 기능만 기능별 패키지로 추가 | 제공된 코드를 건드리지 않아 보존 대상(CORS, `/health`)이 그대로임이 diff로 바로 드러남 | 루트에 설정 · 컨트롤러가 남아 새 기능별 구조와 일관성이 떨어짐 |
| B10-b | 기능 간 의존 | 기능 간 **비즈니스 규칙**을 재사용할 때는 해당 기능의 Service를 거친다. 방향은 댓글 · 좋아요 → 게시글 한쪽으로만. 단, **화면 응답을 만들기 위한 복합 조회**는 조회 쿼리에서 필요한 테이블을 직접 참조할 수 있다 (B10-c) | 게시글 확인 규칙(`POST_NOT_FOUND` · `POST_DELETED`)이 `PostService` 한 곳에만 있고 댓글 · 좋아요가 재사용 | Service 간 의존이 생김. 역방향(게시글 → 댓글 · 좋아요) 호출을 만들지 않도록 주의해야 함 (순환 의존 방지) |
| B10-c | 게시글 응답의 `commentCount` · `likeCount` · `isLiked` | `PostRepository`의 조회 쿼리(JPQL / 네이티브)가 `comments` · `post_like_counts` · `post_likes`를 함께 읽어 집계 | 하나의 조회를 DB에서 한 번(또는 목록 + 묶음 집계)에 처리해 N+1 없음 (B7). SQL 수준의 테이블 참조라 Service 간 역방향 의존이 생기지 않음 (B10-b 유지). 조회 전용 클래스 같은 추가 계층 불필요 | `post/`의 쿼리가 다른 기능의 테이블 구조를 알게 됨 → 해당 테이블이 바뀌면 게시글 조회 쿼리도 함께 수정. JPA 기본 메서드가 아닌 직접 작성 쿼리 (B1에서 감수한 부분) |
| B11 | 요청자 식별 위치 | `HandlerMethodArgumentResolver` + `@CurrentUser` 파라미터 | 요청에서 값을 꺼내 검증해 파라미터로 넣는 Spring의 용도 그대로의 장치. 요청자를 쓰는 API가 메서드 시그니처에 드러남. 선언하지 않은 `/health`에는 자동으로 적용되지 않음. 불일치 시 예외 → 공통 예외 처리기가 C3 형식(`USER_ID_MISMATCH`)으로 응답해 오류 형식이 한 곳에 모임. 단위 테스트가 쉬움 | 애너테이션 · Resolver · 등록 설정이 추가됨. 검사 범위는 `@CurrentUser`를 선언한 API로 한정됨 (B11-a) |

### B10 구현 시 주의 (구현 중 확정)

- `post_like_counts`(`PostLikeCount`)는 게시글당 1행인 "게시글의 좋아요 카운터"이므로 **`post` 패키지가 소유**한다. 게시글 생성 시 `PostService`가 0으로 함께 만든다.
  `like` 패키지에 두면 `PostService → LikeService`(카운터 생성)와 `LikeService → PostService`(게시글 확인 규칙)가 순환 의존이 된다.
- 따라서 좋아요 토글은 규칙(게시글 확인)은 `PostService`를 거치고, 카운터 행의 증감은 `PostLikeCountRepository`로 직접 한다. B8-a 의 테이블 분리(글 수정과 버전 분리)는 그대로다.
- 의존 방향은 `comment → post`, `like → post` 한쪽으로만 유지된다.

### B2 구현 시 주의

- PostgreSQL은 기본값으로 `schema.sql`을 실행하지 않는다 → `spring.sql.init.mode: always`.
- 실행 순서는 기본값(`schema.sql` → JPA `validate`)을 유지한다. `spring.jpa.defer-datasource-initialization: true`를 켜지 않는다.
- 매 기동마다 실행되므로 `CREATE TABLE IF NOT EXISTS` · `CREATE INDEX IF NOT EXISTS`로 작성한다.
- 인덱스 범위는 아래 "인덱스" 절에서 결정 (기본 키 + 유니크 제약만, 잠정).

### B3 · B4 구현 시 주의

- 적재 빈은 `SmartInitializingSingleton.afterSingletonsInstantiated()`에서 실행한다. 이 시점은 모든 싱글톤(Repository 포함)이 준비됐지만 내장 웹 서버는 아직 시작 전이다.
  (`ApplicationRunner` · `ApplicationReadyEvent`는 서버가 열린 뒤라 쓰지 않는다. `ContextRefreshedEvent`도 서버 시작 뒤에 발행된다.)
- 트랜잭션은 `TransactionTemplate`으로 연다. 이 시점의 `@Transactional`은 프록시 적용을 보장하기 어렵다.
- 적재 실패 시 예외를 삼키지 않는다 → 앱 기동 실패 → compose healthcheck 실패로 드러난다. (빈 DB로 조용히 뜨는 것보다 낫다.)
- compose healthcheck 재시도 한도(5초 × 30회) 안에 기동(적재 포함)이 끝나야 한다.
- `HealthController`는 수정하지 않는다.

### B5 구현 시 주의

- `@GeneratedValue` 엔티티는 id를 지정해 저장할 수 없으므로, 시드 INSERT는 JPA가 아닌 SQL(`starter-jdbc`)로 한다.
- `setval`은 게시글 · 댓글 두 테이블 모두, B4 적재 트랜잭션 안에서 실행한다.
- 검증: 시드 적재 직후 게시글 작성 → id 43, 댓글 작성 → id 2077.

### B6 구현 시 주의

- 게시글 삭제는 게시글의 `deleted_at`만 기록한다. 댓글은 건드리지 않는다.
- 시드는 원본 그대로 적재한다. `deletedPostIds` · `deletedCommentIds`에 있는 항목만 `deleted_at`을 기록한다.
  - 기록하는 값은 **적재 시각**(적재 트랜잭션의 현재 시각, 초 단위 — C4). 시드에는 삭제 시각이 없으므로, 세 선택지(적재 시각 / 그 행의 `created_at` / 고정 상수) 중 가짜 의미를 가장 적게 만드는 값을 고름: "이 시스템이 삭제 상태로 기록한 시각"이라는 사실 그대로임.
  - 포기한 것: 실제 삭제 시각이 아니고, 시드 삭제 행 84개가 모두 같은 값을 가짐. `deleted_at` 값은 API에 노출되지 않고 쿼리는 `IS NULL` 여부만 보므로 동작에는 영향 없음.
- 댓글 관련 처리는 항상 부모 게시글 상태를 먼저 확인한다 (C2-c). 게시글이 삭제됐으면 댓글 상태와 관계없이 `POST_DELETED`.
  - 댓글 목록 · 작성: 게시글 확인 후 진행.
  - 댓글 삭제(`DELETE /comments/{id}`): 댓글 → 부모 게시글 상태 → 댓글 상태 → 권한 순으로 확인.
  - `commentCount`: 살아 있는 게시글에만 붙으므로 댓글 `deleted_at IS NULL`만 세면 된다.
- 검증: 시드 9번 게시글의 살아 있는 댓글 id로 `DELETE /comments/{id}` → `POST_DELETED`.

### B7 구현 시 주의

- 목록은 페이지의 게시글 id들에 대해 한 번의 집계 쿼리(`GROUP BY post_id`)로 센다. 게시글마다 따로 세지 않는다 (N+1 방지).
- 댓글이 없는 게시글(시드 10 · 23번)은 0으로 응답한다.
- 검증: 2번 게시글 `commentCount` = 살아 있는 댓글 수 1,411. 댓글 작성 · 삭제 후 즉시 반영.

### B8 구현 시 주의

- 토글은 한 트랜잭션: 게시글 확인(삭제 여부) → `post_like_counts` 조회(버전 포함) → `post_likes` 존재 확인 → 추가 또는 삭제 → `likeCount` ±1 → 커밋 시 버전 검사.
- 게시글 생성과 `post_like_counts` 행 생성(0)은 같은 트랜잭션. 시드 적재 시 시드 `likeCount`로 생성.
- 재시도는 트랜잭션 **바깥**에서 한다. 충돌한 트랜잭션은 롤백되고, 새 트랜잭션에서 처음부터 다시 읽는다.
  재시도 루프와 `@Transactional` 메서드는 별도 빈으로 나누거나 `TransactionTemplate`을 쓴다 (같은 클래스 내부 호출은 프록시를 거치지 않음, tasks T-60).
- `post_like_counts.version`은 0으로 시작한다 (시드 SQL INSERT 포함, tasks T-10).
- 재시도 대상 예외: 낙관적 락 충돌, `post_likes` 유니크 제약 위반.
- **DB 제약 `post_like_counts.like_count >= 0`** (`CHECK`)을 마지막 방어선으로 둔다 (B-42, B14와 같은 방식). `schema.sql`에서만 표현 가능 (B2).
  - 이 제약 위반은 동시성 충돌이 아니라 **버그**이므로 재시도하지 않고 500 `INTERNAL_ERROR`로 응답한다.
  - 유니크 위반과 CHECK 위반은 Spring에서 같은 예외 계열(`DataIntegrityViolationException`)로 올라오므로, 재시도 대상은 **`post_likes` 유니크 제약 위반만** 골라내야 한다 (제약 이름으로 구분).
- **B8-c 재시도 · 실패 응답**: **최초 시도를 포함하여 최대 3회 시도**한다 (= 재시도 최대 2회). 3회 모두 충돌하면 409 `CONCURRENT_UPDATE` (Integration spec §1.5).
  재시도 전에는 지수 백오프 + jitter 로 대기한다 (기준 10ms, n회차 = 10·2^(n-1) ~ 그 2배 ms).
- **충돌을 잡는 장치는 케이스마다 다르다** (둘 다 "일단 쓰고 충돌이면 재시도"하는 낙관적 방식):
  - 안 누른 상태에서 같은 사용자 연타(좋아요 + 좋아요): 두 번째 INSERT 가 `post_likes` 유니크 제약에 걸림 → 재시도 → 취소.
  - 누른 상태에서 연타(취소 + 취소): 커밋 시 `post_like_counts.version` 충돌(또는 DELETE 대상 0행) → 재시도 → 좋아요.
  - 서로 다른 사용자 동시: 기록 INSERT 는 서로 다른 행이라 충돌 없음, 카운터 ±1 에서 `version` 충돌 → 재시도.
- 검증: 같은 사용자 · 같은 글에 동시 요청 2개 → 최종 상태가 원래대로, `like_count` 원래 값. 서로 다른 사용자 N명 동시 요청 → `like_count` 정확히 +N.

### 인덱스

- **결정 (잠정)**: 기본 키 + 유니크 제약(`post_likes (post_id, user_id)`)만 둔다. 추가 인덱스는 만들지 않는다.
- 이유: 현재 데이터 규모(게시글 39, 댓글 2천여 건)에서는 성능 차이가 없음. 측정 없이 미리 추가하지 않는다.
- 포기한 것: 데이터가 늘면 댓글 목록 · 댓글 수 집계가 댓글 전체를 훑음 (PostgreSQL은 외래 키에 인덱스를 자동 생성하지 않음).
- **후속 (시간이 남으면)**: 주요 쿼리를 `EXPLAIN ANALYZE`로 분석해 필요한 인덱스를 근거와 함께 추가한다. 후보:
  - **`commentCount` 집계** (`post_id IN (...)` + `GROUP BY post_id`, 목록 요청마다 실행) — `comments (post_id)` 인덱스. 현재는 셀 때마다 댓글 테이블 전체를 훑음. 같은 인덱스가 댓글 목록 조회에도 쓰임.
  - (참고) 게시글 목록 `total` — 일반 인덱스로는 효과가 작고, 부분 인덱스(`WHERE deleted_at IS NULL`)로 index-only scan이 되는지 확인.
