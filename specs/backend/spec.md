# Backend Spec

Backend가 만족해야 하는 요구사항 (WHAT). 구현 방법과 기술 선택은 `plan.md`에서 다룬다.
상위 문서: `specs/product-spec.md` (`P-xx`). 원본: `ASSIGNMENT.md` §3–5, §7.

> 요청 · 응답 본문의 정확한 형태, 상태 코드, 오류 형식(API 계약)은 `specs/integration/spec.md` §1을 따른다.

---

## 1. 공통

- **B-01 요청자 식별** (P-01~P-03)
  - `x-user-id` **헤더와 쿠키를 모두** 지원한다.
  - 값은 앞뒤 공백을 제거해 사용한다. 비었거나 공백뿐이면 "없음"으로 본다.
  - 한쪽만 유효하면 그 값을 쓴다. 둘 다 없으면 `apr_tester`다.
  - 둘 다 유효한데 서로 다르면 **400**으로 거절하고, 불일치임을 알 수 있는 메시지를 준다.
    이 검사는 **요청자를 식별하는 API**(응답이나 동작이 요청자에 따라 달라지는 API)에서 한다. 댓글 목록 조회처럼 요청자가 필요 없는 API에서는 검사하지 않는다.
  - 작성자 비교와 헤더 · 쿠키 비교는 대소문자를 구분하는 정확한 일치다.
  - `GET /health`에는 적용하지 않는다.
- **B-02 API 경로** — 모든 API는 `/api` 아래에 있다. `GET /health`는 `/api` 밖에 그대로 둔다.
- **B-03 형식** — 요청 · 응답 본문은 JSON이다. 시각은 `ASSIGNMENT.md` 예시와 같은 UTC ISO-8601 형식(`2026-08-30T13:55:54Z`)으로 응답한다.
- **B-04 오류 응답** — 오류 원인을 구분할 수 있어야 한다. 정확한 HTTP 상태 코드와 오류 응답 형태는 integration/spec.md에서 정의한다.
  구분해야 하는 오류: 잘못된 입력 · 잘못된 조회 파라미터 · 요청자 불일치 · 권한 없음(남의 것) · 삭제된 게시글 · 존재하지 않는 게시글 · 삭제된 댓글 · 존재하지 않는 댓글 · 동시 요청 충돌.

## 2. 엔드포인트

| ID | 메서드 · 경로 | 동작 | 관련 |
| --- | --- | --- | --- |
| B-10 | `GET /api/posts` | 게시글 목록, 최신순, 나눠서 조회 | P-10, P-12, P-13 |
| B-11 | `POST /api/posts` | 게시글 작성 `{title, content}`, 작성자 = 요청자 | P-40~P-44 |
| B-12 | `GET /api/posts/{postId}` | 게시글 상세 (단일 객체) | P-20 |
| B-13 | `PATCH /api/posts/{postId}` | 게시글 수정 `{title, content}`, 본인 글만, 수정된 게시글 반환 | P-23, P-24 |
| B-14 | `DELETE /api/posts/{postId}` | 게시글 삭제, 본인 글만 | P-23, P-24, P-50 |
| B-15 | `POST /api/posts/{postId}/likes/toggle` | 좋아요 토글, `{isLiked, likeCount}` 반환 | P-21, P-22 |
| B-16 | `GET /api/posts/{postId}/comments` | 댓글 목록, 최신순, 나눠서 조회 | P-30, P-31 |
| B-17 | `POST /api/posts/{postId}/comments` | 댓글 작성 `{content}`, 작성자 = 요청자 | P-32, P-41 |
| B-18 | `DELETE /api/comments/{commentId}` | 댓글 삭제, 본인 댓글만 | P-33 |

게시글 객체는 `id, title, content, likeCount, commentCount, isLiked, author, createdAt`을 포함한다.
댓글 객체는 `id, postId, content, author, createdAt`을 포함한다.
`isLiked`는 요청자 기준이다. `commentCount`는 삭제되지 않은 댓글 수다.

## 3. 목록 조회 (B-10, B-16)

- **B-20 페이지 크기**
  - 클라이언트가 한 번에 받을 개수(size)를 지정할 수 있다. 생략하면 **20**이다.
  - 허용 범위는 **1~100**이다. 범위 밖(0 이하, 100 초과)이거나 숫자가 아니면 **400**으로 거절한다. 값을 보정하지 않는다.
  - 남은 항목이 요청 개수보다 적으면 있는 만큼 준다. (오류 아님)
  - 게시글과 댓글에 같은 규칙을 적용한다.
- **B-21 이어서 조회** — 다음 묶음을 요청할 수 있어야 한다. 방법은 커서 방식이며, 파라미터 · 응답 필드는 `specs/integration/spec.md` §1.2 · §1.3을 따른다.
  다음 위치를 가리키는 값이 잘못되었으면 **400**으로 거절한다.
- **B-22 전체 개수** — 목록 응답은 `items`와 `total`을 포함한다. `total`은 이번 응답의 개수가 아니라 **조건에 맞는 전체 개수**(삭제 제외)다.
- **B-23 정렬** — 작성 시각 내림차순. 작성 시각이 같은 항목도 항상 동일한 순서를 갖도록 한다.
  데이터에 변경이 없는 동안 이어서 조회했을 때 항목이 중복되거나 누락되지 않아야 한다.
- **B-24** 삭제된 게시글의 댓글 목록 요청은 "삭제된 게시글" 오류로 응답한다. (P-52, P-53)

## 4. 쓰기 규칙

- **B-30 입력 검증** (P-40~P-44)
  - 제목 · 게시글 내용 · 댓글 내용은 필수다. 누락 · 빈 문자열 · 공백과 줄바꿈뿐이면 **400**.
  - 제목은 앞뒤 공백을 제거한 결과가 **1~20 코드포인트**여야 한다. 아니면 **400**.
  - 제목은 앞뒤 공백을 제거해 저장한다. 내용 · 댓글은 받은 그대로 저장한다.
  - 내용 · 댓글 길이 제한은 없다.
- **B-31 수정** — 제목과 내용을 모두 받아 교체한다. 검증 규칙은 작성과 같다.
- **B-32 권한** — 게시글 수정 · 삭제와 댓글 삭제는 작성자 본인만 할 수 있다. 남의 것이면 거절하고 데이터는 바뀌지 않는다.
- **B-33 삭제된 게시글** — 삭제된 게시글에 대한 상세 · 수정 · 삭제 · 좋아요 · 댓글 목록 · 댓글 작성 요청과,
  삭제된 게시글에 달린 댓글의 삭제 요청은 모두 "삭제된 게시글" 오류로 응답한다. 데이터는 바뀌지 않는다.
- **B-34 존재하지 않는 게시글** — "존재하지 않는 게시글" 오류로 응답한다. 삭제된 게시글과 구분한다. (P-53)

## 5. 좋아요 (B-15)

- **B-40** 요청자가 좋아요를 누르지 않은 상태면 좋아요, 누른 상태면 취소한다. 응답은 처리 후 상태다.
- **B-41** 같은 사용자 · 같은 게시글에 대한 좋아요 토글 요청이 동시에 실행되어도,
  각 요청은 하나씩 반영되어야 한다. N개의 토글 요청이 모두 성공하면 최종 상태는 N번 순차적으로 토글한 결과와 같아야 한다.
- **B-42** 좋아요 요청이 성공하면 좋아요 상태와 likeCount 변화가 함께 반영된다. 좋아요 전환 시 likeCount는 1 증가하고,
좋아요 취소 시 1 감소한다. 같은 사용자 · 게시글에 중복된 좋아요 상태가 존재할 수 없으며, likeCount는 음수가 될 수 없다.
- **B-43** 시드 게시글의 좋아요 수는 시드 값에서 시작한다. 시드에는 사용자별 좋아요 기록이 없으므로 모든 요청자의 초기 isLiked는 false다.

## 6. 삭제 (B-14, B-18)

- **B-50** 삭제는 데이터를 지우지 않고 삭제 표시만 남긴다. (P-50)
- **B-51** 삭제된 게시글 · 댓글은 모든 조회 응답(목록 · 상세 · `total` · `commentCount`)에서 제외된다. (P-51)
- **B-52** 게시글이 삭제되면 그 글의 댓글도 삭제된 것으로 취급된다. (P-52)

## 7. 시드 적재

- **B-60** 기동하면 `APP_SEED_PATH`(compose: `/seed/seed.json`)의 데이터가 조회 가능한 상태가 된다. (P-60)
- **B-61** 시드 `id`를 그대로 저장한다. 이후 새로 생성되는 게시글 · 댓글의 id가 시드 id와 충돌하지 않는다. (P-61)
- **B-62** `deletedPostIds` · `deletedCommentIds` 항목은 저장하되 삭제 상태로 둔다. (P-62)
- **B-63** 재기동 시 이미 적재되어 있으면 건너뛴다. 중복 적재되지 않는다. (P-65)
- **B-64** 적재 결과 (검증 시 대조값). 삭제된 데이터도 행으로 저장하므로 **DB 저장 행**과 **API에서 보이는 활성 데이터**를 구분한다.

  | 구분 | 게시글 | 댓글 |
  | --- | --- | --- |
  | DB 저장 행 (삭제 포함) | **42** | **2,076** |
  | 그중 삭제 표시된 행 | 3 (`deletedPostIds`) | 81 (`deletedCommentIds`) |
  | 자기 자신이 삭제되지 않은 행 | 39 | 1,995 |
  | API에서 보이는 활성 데이터 | **39** | **1,926** |

  - 댓글 1,995 → 1,926: 삭제된 게시글(9 · 30 · 31)에 달린 69개는 댓글 행 자체는 삭제 표시가 없지만 부모 게시글 상태로 숨겨진다 (B-52).
  - 재기동 후에도 DB 저장 행은 42 / 2,076 그대로여야 한다 (B-63).
