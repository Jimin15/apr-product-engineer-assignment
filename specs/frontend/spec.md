# Frontend Spec

Frontend가 만족해야 하는 요구사항 (WHAT). 기술 선택과 구현 방법은 `plan.md`에서 다룬다.
상위 문서: `specs/product-spec.md` (`P-xx`). API: `specs/integration/spec.md` (`I-xx` · `C1~C5`).
원본: `ASSIGNMENT.md` §3–4, `design/메디큐브톡.fig`, `README.md`.


---

## 1. 공통

- **F-01 뷰포트** — 모바일 웹, **375px 기준**으로 만든다. 데스크톱 대응은 하지 않는다. (P 범위)
  - 화면 폭은 375px로 고정하고 가운데 정렬한다. 더 넓은 화면에서도 375px로 보이며, 하단 고정 바 · 작성 버튼 · 토스트도 이 375px 안에 둔다 (FD-9).
- **F-02 디자인 반영** — 피그마의 레이아웃 · 색 · 글꼴 · 문구를 최대한 그대로 따른다. 피그마에 없는 부분은 결정 기록에 따라 완성한다.
- **F-03 글꼴** — `frontend/public/fonts/`의 Pretendard를 쓴다 (`globals.css`에 이미 적용).
- **F-04 요청자** — `x-user-id` 쿠키가 요청자다. 쿠키가 없으면 `apr_tester`로 동작한다. `/dev-user` 화면은 수정하지 않는다.
- **F-05 본인 여부** — 게시글 · 댓글의 `author`가 요청자와 같으면 본인 것이다 (대소문자 구분, 정확히 일치, P-02). 본인 여부에 따라 메뉴(⋯) · 댓글 삭제 버튼의 표시가 달라진다.
- **F-06 숫자 표기** — 좋아요 수 · 댓글 수는 천 단위 구분 기호를 쓴다. (피그마: `1,815` · `(1,411)`)
- **F-07 아바타** — `frontend/public/avatar-{1,2,3}.png` 중 하나를 쓴다. 작성자 이름으로 3개 중 하나를 정해, 같은 작성자는 목록 · 상세 · 댓글 어디서나 같은 아바타가 나온다 (채점 제외, FD-7).

### 화면과 이동

```text
목록 (/)  ──항목 클릭──▶  상세 (/posts/{id})  ──⋯ → 수정하기──▶  수정 (작성 화면 재사용) ──완료──▶ 상세 + 토스트
   │                          │
   └──작성 버튼──▶ 작성 ──완료──▶ 목록 + 토스트
                              └──⋯ → 삭제하기 → 다이얼로그 "예"──▶ 목록
```

- **F-08 뒤로 가기** — 상세 · 작성 · 수정 화면의 상단 왼쪽 화살표는 이전 화면으로 돌아간다.
- **F-09 변경 반영** — 작성 · 수정 · 삭제 · 좋아요 · 댓글 작성/삭제 뒤 다른 화면으로 이동하거나 돌아오면 그 결과가 반영되어 보인다. 삭제한 글은 목록에 나오지 않고, 목록의 `likeCount` · `commentCount`도 바뀐 값이다. (과제 §4 삭제 정책 · 수정)

## 2. 게시글 목록

디자인: 상단 바(`메디큐브톡` Bold 20/28, 높이 48, 아래 1px `#eaecee` 테두리) + 항목 반복 + 오른쪽 아래 작성 버튼.

- **F-10 정렬 · 로딩** — 최신순. 첫 화면은 첫 묶음만 받고, 끝까지 내리면 다음 묶음을 이어서 불러온다. 한 번에 전부 받지 않는다. (P-10 · P-12)
- **F-11 항목 구성** (각 항목 높이 118, 하단 구분선 1px `#eaecee` — 좌우 16px 안쪽, 폭 343)
  - 아바타(18px 원) + 작성자 (Regular 12/16 `#5e5e5e`)
  - 제목 (Medium 16/24 `#292828`) — 한 줄, 넘치면 말줄임
  - 내용 미리보기 (Regular 14/18 `#979ea9`) — 한 줄, 넘치면 말줄임
  - 좋아요 아이콘 + 수, 댓글 아이콘 + 수 (아이콘 16px `#dadee3` 외곽선, 숫자 Regular 12/16 `#979ea9`) — 왼쪽 정렬
  - 상대 시간 (Regular 12/16 `#979ea9`) — 오른쪽 정렬
- **F-12 상대 시간** — 현재 시각 기준, 오래된 글도 끝까지 상대 시간으로 표시한다 (FD-2).
  | 경과 | 표기 |
  | --- | --- |
  | 1분 미만 (미래 시각 포함) | `방금 전` |
  | 1분 이상 60분 미만 | `N분 전` |
  | 1시간 이상 24시간 미만 | `N시간 전` |
  | 1일 이상 7일 미만 | `N일 전` |
  | 7일 이상 30일 미만 | `N주 전` (N = 일 ÷ 7, 내림) |
  | 30일 이상 365일 미만 | `N개월 전` (N = 일 ÷ 30, 내림) |
  | 365일 이상 | `N년 전` (N = 일 ÷ 365, 내림) |
- **F-13 작성 버튼** — 오른쪽 아래 고정, 지름 50 원형, 배경 `#c2102f`, 흰색 연필 아이콘(45° 기울어짐). 누르면 작성 화면으로 이동. (P-15)
- **F-14 항목 클릭** — 상세 화면으로 이동. (P-14)
- **F-15 더 없음** — 마지막 묶음(`nextCursor: null`)을 받은 뒤에는 더 요청하지 않는다.
- **F-16 상단 바 오른쪽은 비워 둔다** — 피그마 데이터에 `배지안내` · 알림 아이콘이 있지만, 각각 흰 사각형에 가려져 있거나 숨김 처리되어 화면에는 보이지 않는다. 보이는 그대로 `메디큐브톡`만 둔다.

## 3. 게시글 상세

디자인: 상단 바(테두리 없음, 뒤로 가기, 본인 글이면 오른쪽에 메뉴 버튼) → 본문 영역 → 8px 띠(`#f4f6f9`) → 댓글 영역 → 하단 고정 댓글 입력 바.

- **F-20 본문 구성**
  - 제목 (Bold 18/26 `#292828`) — 여러 줄 허용
  - 아바타(36px) + 작성자 (Bold 15/22) + 작성 시각 (Regular 12/16 `#979ea9`) — 절대 날짜 `YY.MM.DD` (예: `25.08.08`, FD-3)
  - 내용 (Regular 14/18 `#292828`) — 줄바꿈 그대로 표시
  - 좋아요 아이콘(26px) + `좋아요 N` (Regular 13/20 `#979ea9`) — 안 누름: 외곽선 하트 `#979ea9`, 누름: 채운 하트 `#ff8da1`
- **F-21 좋아요 토글** — 누르는 즉시 아이콘과 숫자가 바뀐다 (낙관적 반영). 연타해도 마지막으로 누른 상태가 최종 결과가 된다. (P-21, FD-4)
  - 서버 요청은 같은 게시글 기준 한 번에 하나만 보낸다. 요청 중 추가로 누르면 화면과 "원하는 상태"만 바뀐다.
  - 응답이 오면 서버가 확인한 상태(`isLiked` · `likeCount`)를 기록하고, 원하는 상태와 다르면 토글 요청을 한 번 더 보낸다. 같으면 끝낸다.
  - 실패하면(네트워크 오류 · 409 `CONCURRENT_UPDATE` 등) 게시글을 다시 조회해 화면을 서버 상태로 되돌리고 토스트 `좋아요 처리에 실패했습니다. 잠시 후 다시 시도해 주세요.`를 보여준다.
- **F-22 본인 글 메뉴(⋯)** — 본인 글에만 표시. 피그마 아이콘은 세로 점 3개(⋮, 3×19). 누르면 바텀시트가 열리고 `수정하기` · `삭제하기` (SemiBold 14/22)를 고를 수 있다. 남의 글에는 메뉴가 없다. (P-23 · P-24)
- **F-23 수정하기** — 작성 화면과 같은 화면이 기존 제목 · 내용이 채워진 상태로 열린다 (§5).
- **F-24 삭제하기** — 확인 다이얼로그(§6)에서 `예`를 누르면 삭제 요청 후 **목록 화면으로 이동**하고 토스트 `게시글이 삭제되었습니다.`를 보여준다 (P-25, FD-13). `취소`는 다이얼로그만 닫는다.
- **F-25 삭제되었거나 없는 게시글** — 상세 · 수정 화면에서 `POST_DELETED` · `POST_NOT_FOUND`를 받으면(진입 시 조회, 보는 사이 삭제되어 좋아요 · 댓글 · 수정 저장 · 삭제 중에 알게 된 경우 포함) 알림 다이얼로그(F-53)를 띄운다. 두 코드는 같은 문구로 처리한다. (FD-5)
  - **다이얼로그 뒤에는 삭제된 글의 내용이 보이지 않는다.** 알게 되는 순간 상세 내용 · 댓글 · 하단 입력 바(수정 화면이면 폼)를 지우고 상단 바만 남긴다.
  - `목록으로`를 누르면 목록 화면으로 이동한다.

## 4. 댓글

디자인: `댓글` Bold 16/24 + `(N)` 개수 → 구분선 1px `#ececec` → 댓글 항목 반복 → `댓글 더보기` 버튼 → 하단 입력 바.

- **F-30 정렬** — 최신순. (P-30)
- **F-31 최초 표시** — 상세 진입 시 **최초 2개만** 요청해서 보여준다 (`size=2`).
  - 전체 댓글 수가 3개 이상이면 `댓글 더보기` 버튼(343×42, 흰 배경 + 1px `#e3e3e3` 테두리, r12, Medium 14/24 `#979ea9`, 아래 화살표 아이콘)을 보여준다. 2개 이하면 버튼이 없다.
  - 더보기를 누르면 이어서 다음 묶음을 받고, **그 뒤부터는 끝까지 내릴 때 자동으로** 다음 묶음을 받는다. 더보기 버튼은 다시 보이지 않는다. (P-31)
- **F-32 댓글 수 표기** — 헤더 `(N)`은 서버의 `total`(삭제 제외)이다. 상세 본문의 댓글 수와 같은 값이다.
- **F-33 항목 구성** — 아바타(30px) + 작성자 (Bold 14/22) + 작성 시각 (Regular 12/16 `#979ea9`, 7일 미만이면 F-12 상대 시간 · 7일 이상이면 `YY.MM.DD`, FD-3) + 내용 (Regular 14/18, 줄바꿈 그대로) + 본인 댓글이면 내용 아래 왼쪽에 `삭제` (Regular 12/16 `#979ea9`).
- **F-34 작성** — 하단 고정 입력 바. 빈 값 · 공백만이면 보낼 수 없다 (P-41). 등록되면 목록 맨 위에 보이고 댓글 수가 1 늘어난다.
  - 입력 바: 375×60, 흰 배경, 위 1px `#eaecee` 테두리. 입력창 343×40 (좌우 16px), r20, 1px `#eaecee` 테두리, placeholder `댓글을 입력하세요.` (Regular 15/22 `#979ea9`)
  - 전송 버튼 (피그마 컴포넌트 `입력_active`): 입력창 **안쪽 오른쪽 끝**(테두리에서 6px), 세로 가운데. 지름 28px `#c2102f` 원 + 흰 화살표 아이콘(12×14)
  - 앞뒤 공백을 뺀 값이 **있을 때만** 전송 버튼이 보인다. 비었거나 공백뿐이면 버튼이 없다 (= 보낼 수 없음). 버튼이 나타나도 레이아웃은 밀리지 않는다
  - 엔터는 줄바꿈이다. 전송은 버튼으로만 한다
  - 전송 성공 시 입력창을 비우고 키보드를 닫는다 (새 댓글이 목록 맨 위에 보이도록)
- **F-35 삭제** — 본인 댓글의 `삭제`를 누르면 확인 다이얼로그(§6, 댓글 문구). `예`를 누르면 삭제 요청 후 목록에서 사라지고 댓글 수가 1 줄며, **상세 화면에 머문다**. 삭제 성공 시 토스트 `댓글이 삭제되었습니다.`를 보여준다 (P-36, FD-11). `취소`는 다이얼로그만 닫는다. (P-33)
- **F-36 댓글 없음** — 댓글이 0개인 동안 헤더 `댓글 (0)` 아래 댓글 목록 자리에 `아직 댓글이 없습니다.` (Regular 14/18 `#979ea9`, 가운데 정렬, 위아래 여백 40px)를 계속 표시한다. 댓글이 생기면 사라지고, 삭제로 다시 0개가 되면 다시 보인다. 토스트가 아닌 화면 고정 문구다. (P-35, FD-6)

## 5. 작성 · 수정

디자인: 상단 바(테두리 없음, 뒤로 가기만) → 그 아래 왼쪽 라벨 `글작성` (Bold 14/22) → 제목 입력 → 내용 입력 → 하단 고정 `작성 완료` 버튼(343×56, r12).

- **F-40 입력 필드**
  - 제목: placeholder `제목을 입력해 주세요. (최대 20자)`, 아래 1px 밑줄 (비어 있으면 `#f3f4f8`, 값이 있으면 `#292828`). 입력된 글자는 Regular 14/18 `#292828`. 포커스 상태는 피그마에 없음
  - 내용: placeholder `게시글 내용을 작성해주세요.\n부적합한 내용은 삭제될 수 있으며, 비방/욕설 등의 내용으로 신고가 접수될 경우 서비스 이용이 제한될 수 있습니다.`, 여러 줄
- **F-41 완료 버튼 상태** — 제목과 내용이 **둘 다 유효**할 때만 활성(`#292828`, 흰 글씨). 하나라도 비어 있거나 공백뿐이면 비활성(`#dadee3`, 흰 글씨)이고 누를 수 없다. 글자는 두 상태 모두 Bold 16/24. (P-40 · P-41)
- **F-42 제목 20자** — 제목 길이는 유니코드 코드포인트 기준으로 20자를 초과할 수 없다. (P-42)
  - 글자 수 표시 (P-47, FD-12): 제목 입력 줄 오른쪽 끝, 밑줄 위에 `N / 20` (Regular 12/16 `#979ea9`). `0 / 20`부터 항상 보인다.
  - 20자에 닿으면 숫자를 `#c2102f`로 바꾼다. 별도 오류 문구는 없다.
  - N은 서버와 같은 코드포인트 기준이다. 피부색이 붙은 이모지(`🙏🏻`)처럼 눈에는 1개여도 2 이상 늘 수 있다.
  - 작성 · 수정 화면 모두 적용한다.
- **F-43 작성 완료** — 저장 성공 시 **목록 화면으로 이동**하고 토스트 `게시글이 등록되었습니다.`를 보여준다. 새 글이 목록 맨 위에 보인다. (P-45)
- **F-44 수정 화면** — 작성 화면과 구성이 동일하며 기존 제목 · 내용이 채워진 채 열린다. 제약은 작성과 같다. 저장하면 바뀐 제목 · 내용이 상세와 목록에 반영된다 (F-09). (P-23, FD-8)
  - 라벨은 `글수정`, 버튼은 `수정 완료` (스타일 · 활성 조건은 작성과 같음)
  - 저장 성공 시 **상세 화면으로 돌아가고** 토스트 `게시글이 수정되었습니다.`를 보여준다. 이후 뒤로 가기를 눌러도 수정 화면이 다시 나오지 않는다.
- **F-45 서버 검증 실패** — 서버가 입력 검증 오류를 반환하면 사용자가 오류를 인지할 수 있도록 표시한다. 구체적인 오류 응답 구조는 Integration Spec을 따른다.
- **F-46 작성 · 수정 중 이탈 확인** — 상단 왼쪽 **뒤로 가기 화살표**를 눌렀을 때 아래 조건이면 바로 나가지 않고 이탈 확인 다이얼로그(F-52)를 띄운다. 조건이 아니면 바로 이전 화면으로 간다. (P-46, FD-10)
  - 작성: 제목 또는 내용에 공백이 아닌 글자가 하나라도 있음
  - 수정: 제목 또는 내용이 처음 채워진 값과 달라짐
  - 저장 성공으로 이동할 때는 묻지 않는다. 브라우저 뒤로 가기 · 새로고침 · 탭 닫기는 대상이 아니다.
- **F-47 남의 글 수정 화면 진입** — 주소로 남의 글 수정 화면(`/posts/{id}/edit`)에 들어오면 수정 폼을 보여주지 않고 상세 화면으로 보내며 토스트 `다른 사람의 글은 수정할 수 없습니다.`를 보여준다. 본인 글인지 확인하는 동안에도 폼은 보이지 않는다. 삭제됐거나 없는 글이면 F-25를 따른다. (P-24, FD-14)

- **F-60 토스트** — 검정 70% 불투명(`#000` · opacity 0.7) 배경, 높이 40 · 가로는 문구 길이에 맞춤(좌우 20px 여백, 피그마 예시 181×40), r6, 흰 글씨 Regular 14/18, 화면 하단 가운데. 일정 시간 뒤 자동으로 사라진다. (시간은 plan)

- **F-62 오류 표시** — 서버 오류 또는 네트워크 오류가 발생하면 사용자에게 실패 사실을 알린다. 오류별 처리 방식은 Integration Spec의 오류 계약을 따른다.
- **F-63 불러오기 실패 안내** — 목록 · 상세의 첫 로딩, 댓글 목록의 첫 로딩, 무한 스크롤의 다음 묶음을 불러오지 못하면 토스트가 아니라 그 자리에 `불러오지 못했습니다.`와 `다시 시도` 버튼을 보여준다. `다시 시도`를 누르면 같은 요청을 다시 보낸다. 피그마에 없는 요소라 버튼은 `댓글 더보기` 버튼 디자인(F-31)을 재사용한다. (FD-15)

## 결정 기록

- **FD-1 댓글 전송 방식** — 값이 있을 때만 전송 버튼 표시 · 엔터는 줄바꿈 · 전송 후 입력창 비우고 키보드 닫기 (F-34).
  이유: 피그마의 두 변형(`입력` = 버튼 없음, `입력_active` = 버튼)에 그대로 대응해 없는 디자인(비활성 버튼)을 만들 필요가 없고, 버튼의 존재가 곧 "보낼 수 있음"이라 빈 값 차단이 자연스럽다.
  포기한 것: 입력 전에는 전송 수단이 보이지 않음 (댓글 입력이 먼저인 흐름이라 영향 작음), 엔터 전송의 편의.
- **FD-2 상대 시간 규칙** — 목록은 끝까지 상대 시간 (`N주 전` · `N개월 전` · `N년 전`까지, F-12).
  이유: 과제가 목록을 상대 시간으로 명시했고, 시드 글 대부분이 수 주 이상 지나 "일정 기간 뒤 절대 날짜"로 바꾸면 목록 대부분이 날짜로 표시된다.
  포기한 것: 오래된 글의 정확한 날짜를 목록에서 바로 알 수 없음 (상세에서 확인 가능).
- **FD-3 상세 · 댓글 시각** — 피그마대로: 게시글은 `YY.MM.DD`, 댓글은 7일 미만 상대 시간 · 7일 이상 `YY.MM.DD`.
  이유: 피그마의 게시글 `25.08.08` 과 댓글 `13시간 전` · `25.05.13` 혼재를 "최근은 상대, 오래되면 날짜"로 해석. 과제는 목록만 상대 시간을 요구한다.
  포기한 것: 목록 · 상세 · 댓글의 표기 일관성.
- **FD-4 좋아요 낙관적 반영** — 즉시 반영 + 게시글당 요청 하나씩 + 원하는 상태와 서버 확인 상태 비교 후 필요하면 한 번 더 토글 + 실패 시 재조회로 복구 (F-21).
  이유: 실제 앱(인스타그램 · 유튜브 등)처럼 누르는 즉시 반응해야 불편하지 않다. API가 "설정"이 아닌 "토글"이라 연타마다 요청하면 응답이 엇갈리므로 요청을 하나씩 보내고 마지막 상태로 수렴시킨다.
  포기한 것: 단순함 — 화면 값과 서버 확인 값 두 상태를 관리하고 복구 처리가 필요하다.
- **FD-5 없는 글 상세** — 삭제 확인 다이얼로그 디자인을 따른 알림 다이얼로그: 제목 없이 문구 + `목록으로` 버튼 하나 (F-25 · F-53).
  이유: 무슨 일인지 바로 알 수 있고, 주소를 직접 입력해 들어온 경우에도 자연스럽다. 기존 다이얼로그 디자인을 재사용해 새 디자인 없이 일관성을 유지하고, 의미 없는 제목을 지어내지 않도록 제목은 두지 않는다. 두 오류 코드는 사용자 입장에서 차이가 없어 문구를 하나로 둔다.
  보던 중 삭제된 경우 뒤에 삭제된 글이 비쳐 보이면 "완전히 사라진 것처럼"(과제 삭제 정책)과 어긋나므로, 다이얼로그를 띄울 때 뒤의 내용을 지운다.
  포기한 것: 자동 이동의 빠름 — 한 번 더 눌러야 목록으로 간다.
- **FD-6 댓글 0개 문구** — `아직 댓글이 없습니다.`를 목록 자리에 고정 표시 (F-36). 피그마에 없는 요소 → README "개선한 점"에 기록.
  이유: 피그마는 빈 공간뿐이라 불러오는 중 · 오류 · 0개를 한눈에 구분하기 어렵다. 입력창 placeholder가 이미 행동을 유도하므로 문구는 상태만 알린다.
  포기한 것: 피그마와의 완전한 일치.
- **FD-7 아바타** — 작성자 이름 기준 고정 (F-07). 이유: 같은 사람을 알아보기 쉽다. 포기한 것: 없음 (채점 제외 항목).
- **FD-8 수정 화면** — 라벨 `글수정` · 버튼 `수정 완료`, 저장 후 상세로 복귀 + 토스트 `게시글이 수정되었습니다.` (F-44).
  이유: 상세에서 들어온 흐름이라 고친 결과를 바로 확인하는 것이 자연스럽다. 과제의 "작성 화면과 동일"은 화면 구성과 기존 값이 채워진 상태로 해석하고, 문구만 지금 하는 일에 맞춘다. 토스트는 작성 완료와 같은 스타일 · 말투.
  포기한 것: 과제 문구에 글자 그대로 맞추는 것 (`글작성` · `작성 완료` 유지).
- **FD-9 화면 폭** — 375px 고정 · 가운데 정렬 (F-01).
  이유: 과제가 375px 기준 · 데스크톱 대응 불필요를 명시했고, 피그마와 같은 폭으로 보인다.
  포기한 것: 375px보다 넓은 실제 폰(390~430px)에서도 양옆에 빈 영역이 생긴다.
- **FD-10 작성 · 수정 중 이탈 확인** — 뒤로 가기 화살표에만 확인 다이얼로그 (F-46 · F-52). 피그마 · 과제에 없는 추가 → README "개선한 점"에 기록.
  이유: 실수로 뒤로 가서 입력한 글을 잃는 일을 막는다. 수정은 "바뀌었을 때만" 물어 아무것도 고치지 않았을 때 불필요하게 묻지 않는다. 다이얼로그는 삭제 확인 디자인을 재사용해 새 디자인 없이 일관성을 유지한다.
  포기한 것: 브라우저 뒤로 가기 · 새로고침 · 탭 닫기로 나가는 경우는 막지 않는다 (App Router에 공식 방법이 없어 우회가 필요).
- **FD-11 댓글 삭제 토스트** — 삭제 성공 시 `댓글이 삭제되었습니다.` 토스트 (F-35). 피그마 · 과제에 없는 추가 → README "개선한 점"에 기록.
  이유: 댓글이 바로 사라져도 삭제가 실제로 처리됐다는 확인을 준다. 작성 완료 토스트와 같은 스타일 · 말투.
  포기한 것: 없음 (기존 토스트 재사용).
- **FD-12 제목 글자 수 표시** — 제목 줄 오른쪽 `N / 20` 항상 표시, 20자에서 `#c2102f` (F-42). 피그마 · 과제에 없는 추가 → README "개선한 점"에 기록.
  이유: 입력을 시작하면 placeholder의 "(최대 20자)" 안내가 사라져, 21번째 글자가 막힐 때 이유를 알 수 없다. 숫자 색만 바꿔 오류가 아닌 "한도 도달"로 보여준다.
  포기한 것: 이모지 등은 눈에 보이는 개수와 숫자가 다를 수 있다 (서버 검증 기준과 일치시키는 쪽을 택함).
- **FD-13 게시글 삭제 토스트** — 삭제 후 목록에서 `게시글이 삭제되었습니다.` 토스트 (F-24). 댓글 작성에는 토스트를 두지 않는다. 피그마 · 과제에 없는 추가 → README "개선한 점"에 기록.
  이유: 삭제 후 곧바로 목록으로 이동해 삭제가 됐는지 오류로 나간 건지 헷갈릴 수 있다. 댓글 삭제 토스트(FD-11)와 일관된다. 댓글 작성은 새 댓글이 바로 맨 위에 보여 그 자체로 확인이 된다.
  포기한 것: 없음 (기존 토스트 재사용).
- **FD-14 남의 글 수정 화면 진입** — 폼을 보여주지 않고 상세로 보내며 토스트 `다른 사람의 글은 수정할 수 없습니다.` (F-47).
  이유: 과제는 "남의 게시글은 수정할 수 없다"고만 해서 주소로 직접 들어온 경우가 비어 있다. 폼을 보여준 뒤 저장할 때 거절하면 입력한 내용을 잃게 되므로 들어오는 시점에 막는다.
  포기한 것: 확인하는 동안 잠깐 로딩 화면이 보인다.
- **FD-15 불러오기 실패 안내** — 첫 로딩 · 다음 묶음 실패는 인라인 `불러오지 못했습니다.` + `다시 시도` (F-63). 피그마 · 과제에 없는 추가 → README "개선한 점"에 기록.
  이유: 토스트만 띄우면 사라진 뒤 빈 화면(또는 더 이상 불러오지 않는 목록)만 남는다. 첫 로딩 실패는 화면 자체가 성립하지 않는 상태라 그 자리에 안내와 재시도 수단을 둔다.
  포기한 것: 없음 (기존 버튼 디자인 재사용).
